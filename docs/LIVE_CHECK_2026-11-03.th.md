## สถานะล่าสุด

แก้เส้นทางรับภาพบน Windows แล้ว โดยใช้ go2rtc ใน Docker สำหรับ TCP/TLS และตัวส่ง UDP แบบยืนยันตัวตนบน Windows สำหรับ Xiaomi CS2 ไม่ได้ปิดไฟร์วอลล์หรือโปรแกรมป้องกันเครื่อง ไม่เปลี่ยนเฟิร์มแวร์ ไม่รีเซ็ตกล้อง และใช้บัญชีเดิม

ตรวจวิดีโอจริงและการเปลี่ยนตำแหน่งมอเตอร์ครบสี่ทิศทางได้ **12 กล้อง** จากรายการกล้อง 16 ตัว อีก 1 รายการในระบบเป็น Indoor Receiver จึงรวมรายชื่อบนเว็บ 17 รายการ ยังไม่ถือว่าตรวจรับอุปกรณ์ครบทุกตัวหรือทดสอบระยะยาวผ่าน

ตรวจคำสั่ง Xiaomi แบบก้าวสั้น ๆ 1–4 แล้วอ่านตำแหน่งด้วย operation 6 ก่อนและหลังคำสั่ง ไม่ใช้ HTTP 200 หรือ ret:0 อย่างเดียวเป็นหลักฐานว่าหมุนได้ แก้ตัวอ่านตำแหน่งให้รับเลขทศนิยมที่ C302 ส่งจริง เช่น angle 57.48 โดยไม่ปัดทิ้ง ยังไม่ติ๊ก PTZVerified หรือ AudioVerified แทนเจ้าของ ต้องดูภาพยืนยันทิศทางกับเสียงเพิ่มเติมเมื่อสะดวก

Tapo92 ตรวจผ่านหน้าเว็บด้วย: กดขวาค้าง 350ms แล้วปล่อย ตำแหน่ง pan จาก 0 เป็น 0.031746 หลังจากนั้นกดซ้ายกลับได้ประมาณ -0.003968 โดย tilt คง -0.75 การตรวจสี่ทิศทางก่อนหน้านั้นใช้ AbsoluteMove คืนค่าเดิม 0/-0.75 และอ่านซ้ำหลังหยุดได้ค่าเดิม

## ตัวเปิดระบบ Windows

ใช้ `Start-CameraHub-Live.cmd` ตามเดิม ต้องเปิด Docker Desktop ให้พร้อม และเครื่องนี้มี Node.js ใช้งานอยู่แล้ว ตัวเปิดอ่านโหมด `docker-relay` จากไฟล์ส่วนตัวและเปิดทั้งสองส่วนให้เอง

- หน้าดูภาพ: http://127.0.0.1:17801/ เฉพาะเครื่องกลางนี้ ไม่ใช่ลิงก์ดูนอกบ้าน
- API go2rtc อยู่ในเครือข่าย Docker มีรหัสยืนยันตัวตน ไม่เผยแพร่พอร์ต API/RTSP ของ gateway ออกสู่ LAN
- ตัวส่ง UDP ใช้ loopback 127.0.0.1:17993 มีโทเคนบริการและรับเฉพาะ IP กล้อง Xiaomi ที่บันทึกใน registry ไม่เปิด UDP proxy สำหรับปลายทางใดก็ได้
- `relay-hosts.json` สร้างจาก SQLite เมื่อเริ่มแอปและหลังซิงก์ บัญชี/โทเคนไม่อยู่ในรายชื่อ IP ตัวส่งอ่านรายชื่อใหม่ทุกการเชื่อมต่อ จึงรองรับเพิ่มกล้องและเปลี่ยน IP โดยไม่ต้องสแกนเครือข่ายเอง
- ตั้ง TCP no-delay และขยาย receive buffer สำหรับแพ็กเก็ต/ACK จำนวนมากของ CS2
- ข้อมูลยังอยู่ใน Docker volume live-data เดิม และ data/windows-live-gateway เดิม ไม่มีการขอบัญชี/รหัสผ่านใหม่

ตัวกลาง Go native เดิมและโปรแกรมตรวจเครือข่าย Go บางโปรเซสยังถูก Windows ถือค้างหลังสั่งหยุด เส้นทางใหม่ไม่ใช้โปรเซสเหล่านั้น ไม่เปิด native เพิ่ม ไม่สรุปว่าเกิดจากโปรแกรมป้องกันหรือไดรเวอร์ใด เปรียบเทียบโปรแกรม Go ทดสอบสั้น ๆ แล้วค้างเช่นกัน ขณะที่ .NET/Node ติดต่อกล้องได้ จึงเปลี่ยนเส้นทางโดยไม่ลดการป้องกันเครื่อง

## ผลตรวจซอฟต์แวร์และวงจรบริการ

- Go tests 26 ฟังก์ชันทดสอบและ go vet ผ่าน รวมเลขทศนิยม C302 และรายชื่อ relay ที่ยอมให้เฉพาะกล้อง Xiaomi IP ส่วนตัวใน registry และนำรายการที่ลบออกจากสิทธิ์ได้
- Node relay tests 3 ข้อผ่าน: ปฏิเสธโทเคน/ปลายทางผิด, ส่งกรอบแพ็กเก็ตและพอร์ตที่กล้องเจรจาจริง, อ่าน allowlist ที่เปลี่ยนใหม่
- go2rtc CS2 relay framing/bounds fixture ผ่าน และ motor reply framing fixture จาก patch เดิมผ่าน
- สร้าง app/gateway Docker amd64 ผ่าน ตรวจ Start/Start ซ้ำ PID เดิม, Stop พอร์ต relay ปิด, Start ใหม่และ health ของแอปผ่าน
- ผู้ไม่เข้าสู่ระบบเรียกรายชื่อ/วิดีโอ CameraHub ได้ 401 และ gateway API ที่ไม่ส่งรหัสได้ 401 เช่นกัน
- Chrome เปิด Tapo92 มีเฟรมจริง ปุ่มหมุนขวา/ซ้ายทำให้ตำแหน่งเปลี่ยน และ C302 H1 เปิดวิดีโอพร้อมปุ่มตรวจระบบหมุนอ่านตำแหน่งทศนิยมผ่าน
- เปิด Tapo92/H1/Mi360/C300 พร้อมกัน 4 ภาพมากกว่า 3 นาที ทุกตัว readyState4 และมีความกว้างภาพจริง เทียบสองช่วง currentTime เดินเพิ่มประมาณ103–108วินาทีโดยไม่กลับไปเริ่ม0 เก็บภาพหน้าจอและค่าตรวจใน .cache ภายในเครื่อง ไม่ใช่การรับรองหลายชั่วโมงหรือทุกช่องพร้อมกัน
- ช่องที่มีผลตรวจ error แสดงพื้นดำและสาเหตุล่าสุดทันทีระหว่างลองเชื่อมต่อใหม่ ไม่ต้องรอให้หมดเวลาเปิดภาพ เมื่อได้เฟรมใหม่จริงข้อความจึงหาย
- ตรวจ Tapo91 ผ่าน UI หลังติดตั้งรุ่นสุดท้ายแล้ว: พื้นหลัง rgb(0,0,0) พร้อมข้อความ “ยังรับภาพจาก IP ล่าสุดในบัญชีไม่ได้…” และสถานะกำลังลองใหม่ แยกจากผลตรวจ12กล้องที่มีภาพจริง

ภาพจำลองไม่ใช่หลักฐานในรายงานนี้ การตรวจวิดีโอแต่ละตัวใช้ MP4 video fragments จริง ไม่ยืนยันจาก init/metadata/audio อย่างเดียว บันทึกตัวรันภาคสนามที่แสดง PASS หมายถึงรันจบ ต้องอ่าน result ของแต่ละกล้องประกอบ
