# ตัวรับภาพบน Windows สำหรับ Xiaomi

**ล่าสุดช่วงเย็น3พฤศจิกายน:** ตรวจระยะไกลผ่านภาพ/มอเตอร์15กล้องและรับ/ถอดรหัสเสียง15 เหลือTapo91ไม่ตอบเครือข่ายกับอีก1รายการReceiver เพิ่มกู้ภาพต่อเนื่องและทดสอบหยุด/เปิดgatewayแล้วภาพ4ช่องกลับมาเอง อ่าน [รายงานรอบเย็น](REMOTE_CHECK_2026-11-03.th.md) สถานะ12กล้องด้านล่างเป็นประวัติ

**ล่าสุด 3 พฤศจิกายน:** ใช้โหมด Docker gateway + Windows UDP relay แทน Go native ที่ค้าง ตัวเปิดเดิมเลือกโปรไฟล์ใหม่ให้อัตโนมัติ API gateway ไม่publishพอร์ต ส่วน relay อยู่loopback17993และต้องauth/จำกัดIPจากregistry รับภาพและหมุนผ่าน12กล้อง อ่าน [ผลตรวจและโครงสร้างปัจจุบัน](LIVE_CHECK_2026-11-03.th.md) ข้อมูลพอร์ตnative17984/17992และปัญหาข้างล่างเป็นประวัติ ห้ามสั่งย้ายกลับเพียงเพราะอ่านหัวข้อเก่า

**ล่าสุด 2 พฤศจิกายน 17:30:** ตัวกลาง Windows เชื่อมต่อขาออกค้าง ยังไม่ผ่านตรวจภาพ/หมุนรอบนี้ เสนอเจ้าของรีสตาร์ต Windows เองหลังบันทึกงาน โดยไม่รับรองว่าจะหาย ปัจจุบันเตรียม API loopback17992/RTSP18562 และ go2rtc.startup.exe ที่ตรวจ hash ก่อนคัดลอกโปรแกรมไป immutable cache ใน LocalAppData บัญชี/keys อยู่ data เดิม ไม่มี debug ใน config ปัจจุบัน มีโปรเซสการตรวจบางตัวยังหยุดไม่สำเร็จ จึงไม่เปิดตัวกลางเพิ่ม อ่าน [สถานะล่าสุด](PICKER_UPDATE.th.md) ก่อนผลตรวจและพอร์ตเก่าด้านล่าง

ผลตรวจจริง 2 พฤศจิกายน 2026: C300 ชื่อ “Xiaomi Smart Camera C300” รุ่น xiaomi.camera.c01a01 ที่เจ้าของยืนยันว่าดูในมือถือได้ ตอบ CS2 discovery จาก Windows แต่ไม่ตอบเข้าคอนเทนเนอร์ Docker Desktop ตัวทดสอบได้รับคำตอบ f141 จากพอร์ตกล้องที่ต่างจาก 32108 จึงย้ายตัวรับภาพของ Windows live มาทำงานบน Windows โดยตรง หลังเปลี่ยนเส้นทาง Chrome แสดงภาพจริง C300 และ Tapo92 พร้อมกันได้ ภาพทั้งสองช่อง 640×360 มีเฟรมและเวลาเดิน ผลนี้ไม่ยืนยัน Xiaomi ทุกตัวหรือทุกโมเดล

## เปิดใช้งานครั้งต่อไปบนเครื่องนี้

เปิด Docker Desktop แล้วดับเบิลคลิก `Start-CameraHub-Live.cmd` จาก File Explorer เช่นเดิม เข้าที่ <http://127.0.0.1:17801/> ไม่ต้องสร้างเจ้าของระบบ เชื่อมบัญชี Xiaomi หรือเพิ่มกล้องเดิมซ้ำ ตัวเปิดตรวจ `data/windows-live-gateway/native.json` และเปิดตัวรับภาพ Windows ให้เอง หยุดด้วย `scripts/Stop-Live.ps1` ซึ่งหยุดทั้งเว็บและตัวรับภาพโดยเก็บข้อมูลไว้ เครื่อง Windows และ Docker ต้องทำงานขณะใช้งาน

## การแยกงานและข้อมูล

- เว็บ/API และ SQLite ยังอยู่ในคอนเทนเนอร์ app และ volume live-data เดิม
- go2rtc บน Windows สร้างจาก commit และ control patch ที่ตรึงไว้ชุดเดียวกับ Docker ผ่าน `scripts/Build-WindowsGateway.ps1`; มี SHA-256 ตรวจความครบของไฟล์ก่อนเริ่ม
- ตัวกลางเปิด API เฉพาะ `127.0.0.1:17984` พร้อมรหัสบริการสุ่มและ `local_auth: true`; RTSP ผูก loopback `18554` พร้อมรหัสเช่นกัน ไม่เปิด WebRTC listener
- app ติดต่อ loopback ของ Windows ผ่าน `host.docker.internal` ซึ่งตรวจว่าทำงานได้บนเครื่องนี้ บราวเซอร์ยังผ่านการเข้าสู่ระบบ CameraHub เช่นเดิม ไม่เปิด API ตัวกลางให้ LAN และไม่ได้แก้ Windows Firewall/เราเตอร์
- `data/windows-live-gateway` จำกัด ACL ให้ผู้ใช้ Windows ปัจจุบันและ SYSTEM เท่านั้น เก็บ go2rtc.yaml, native.json และ log ส่วนตัว ห้ามส่งไฟล์หรือ log เหล่านี้ในแชต/ชุดติดตั้ง
- go2rtc อ่าน go2rtc.yaml เดิมก่อนแล้วใช้ native.json ทับเฉพาะการฟังพอร์ต/รหัสบริการ เมื่อซิงก์หรือเชื่อมบัญชีใหม่ยังเขียนใน go2rtc.yaml ตัวเดิม app mount โฟลเดอร์นี้ที่ /gateway-state จึงสำรองข้อมูล gateway จากไฟล์ที่ใช้งานจริง
- เก็บ Docker gateway volume เดิมไว้สำหรับย้อนกลับ ไม่ลบ volumes และไม่คัดลอกข้อมูลส่วนตัวไป releases

## เครื่องใหม่หรือกลับไปใช้ Docker

บนเครื่องใหม่ให้เปิด Windows live และตั้งระบบก่อน หากพบปัญหา CS2 ผ่าน Docker จึงรัน `scripts/Enable-WindowsGateway.ps1` ตัวเปิดจะหยุดผู้เขียนข้อมูล คัดลอก config เดิม และเปิดเส้นทาง Windows ไม่ต้องกรอกรหัสกล้องใหม่

กลับไป Docker ด้วย `scripts/Disable-WindowsGateway.ps1` ซึ่งหยุดทั้งสองบริการ คัดลอก config ล่าสุดกลับ volume เดิม เก็บ config ก่อนย้อนกลับ แล้วเปิดบริการ Docker ไม่แก้ฐานข้อมูลกล้อง หลังย้อนกลับสามารถรัน Enable ได้อีก การสลับนี้ผ่านทดสอบบนเครื่องปัจจุบันแล้ว แต่ Docker กลับไปมีข้อจำกัด CS2 เดิม จึงไม่ใช่วิธีแก้ภาพ Xiaomi

## ผลตรวจและขอบเขต

ผ่าน: HTTP API ตัวกลางปฏิเสธผู้ไม่ยืนยันตัวตนด้วย 401, listener เป็น loopback เท่านั้น, app health ปกติ, เปิดภาพจริงคู่ Tapo92/C300 ใน Chrome, ผลตรวจภาพ C300 บันทึกเป็น stream_only โดยไม่ยืนยันเสียง/PTZ, หยุดแล้วพอร์ตปิด, เปิดใหม่, เริ่มซ้ำโดยไม่สร้าง gateway ซ้ำ, ย้อนกลับ Docker และเปิด Windows อีกครั้งโดยข้อมูลเดิมยังอยู่

ตรวจเพิ่มเติมหลังเริ่มระบบใหม่: C300 readyState4 เวลาเดินจากประมาณ38เป็น86วินาที ภาพ640×360; Tapo92เวลาเดินจากประมาณ40เป็น74วินาที แต่พบช่วง buffering (readyState1) จึงไม่รับรองความลื่น/เสถียรภาพของ Tapo92 จากการทดสอบคู่ครั้งนี้ ตรวจ syntax PowerShell ที่เปลี่ยนทั้ง8ไฟล์ผ่าน และ CameraHub /api/cameras ปฏิเสธผู้ไม่เข้าใช้ด้วย401 มี gateway ในworkspaceทำงานเพียง1process

ยังไม่ตรวจ: กล้อง Xiaomi อื่น, เสียง/PTZ/HD, เปิดหลายชั่วโมง, iPhone/Android/TV, NAS DS223 และดูนอกบ้าน กล้อง C300 ส่ง H.265/Opus และ Chrome เครื่องนี้เล่นภาพได้ อุปกรณ์อื่นอาจต้องโปรไฟล์แปลง H.264 ซึ่งต้องมี FFmpeg บน Windows (เครื่องนี้มี FFmpeg อยู่แล้ว) การแปลงภาพและประสิทธิภาพยังไม่รับรอง

ตัวกลางแบบนี้เป็นทางเลือกสำหรับ Windows เท่านั้น ไม่เปลี่ยนชุด NAS ต้องตรวจเส้นทาง UDP ของ NAS จริงก่อนติดตั้ง ไม่ถือว่าทดสอบ Docker ARM64/NAS ผ่านจากผล Windows

ชุด ZIP/APK/ARM64 ใน releases ยังเก่ากว่างานรอบนี้ ต้องสร้างใหม่และตรวจ checksum ก่อนส่งเครื่องอื่น Package-Release.ps1 เตรียม allowlist สำหรับตัวเปิดและ binary Windows แล้ว แต่ยังไม่ได้รันสร้างชุดใหม่

อ้างอิงประกอบการวิเคราะห์: [Docker Desktop networking](https://docs.docker.com/desktop/features/networking/) และ [รายงาน CS2 UDP ผ่าน Docker bridge ของ go2rtc](https://github.com/AlexxIT/go2rtc/issues/2514) กลไก NAT ที่แน่นอนของเครื่องนี้ยังไม่ได้จับ packet capture ครบทุกชั้น ผลเปรียบเทียบ Windows/Docker และภาพจริงหลังสลับเส้นทางเป็นหลักฐานที่ตรวจบนเครื่องนี้
